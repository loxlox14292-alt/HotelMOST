# HotelMOST — учебная система управления отелем

Курсовой проект на **Python, PyQt6 и MySQL**: desktop-приложение с отдельными интерфейсами администратора, менеджера и гостя. Это учебный прототип, а не backend-сервис и не готовая система для настоящего отеля.

Проект демонстрирует работу с графическим интерфейсом, реляционной базой данных, параметризованными SQL-запросами, транзакциями и PDF-отчётами. Демонстрационные записи не содержат данных настоящих гостей.

## Возможности

- Вход с тремя ролями; регистрация новых пользователей с ролью гостя.
- Гость: поиск номеров по датам с проверкой пересечения существующих заявок и заездов, создание заявки на бронирование.
- Менеджер: оформление заезда, расчёт стоимости по количеству ночей, оформление выезда и перевод номера на уборку.
- Администратор: добавление номеров, просмотр номерного фонда, пользователей и бронирований.
- Аналитика: загрузка номеров, суммы активных и завершённых бронирований, активные заезды и новые заявки; помесячная диаграмма. Показатель «выручка» не является учётом фактически проведённых платежей.
- Экспорт двухстраничного PDF с показателями, диаграммами и помесячной сводкой через `QPainter` / `QPdfWriter`.

## Стек

Python · PyQt6 · MySQL · PyMySQL · SQL. Зависимости приложения перечислены в `requirements.txt`; `cryptography` используется драйвером при соответствующих методах авторизации MySQL.

## Локальный запуск

Понадобятся Python 3.11 или новее, MySQL 8.x и графическая среда. Команды выполняются из корня проекта. На Linux должен быть доступен рабочий Qt-сеанс (X11 или Wayland).

### 1. Подготовить отдельную учебную базу

**Не импортируйте `database.sql` на сервер с рабочими данными.** Скрипт создаёт базу `hotel_db`, пользователя `hotel_course_admin` с правами на эту базу, таблицы и demo-записи. Повторный запуск может обновить роли demo-пользователей и параметры номеров. Используйте новый локальный учебный сервер либо сначала проверьте, что эти имена не заняты вашими данными.

1. Установите и запустите MySQL.
2. Подключитесь к отдельному локальному серверу через MySQL Workbench или другой SQL-клиент с правами создания базы и пользователя.
3. Откройте `database.sql`, замените публичный пароль `dev_only_change_me` на свой локальный пароль и выполните скрипт.
4. Перед запуском приложения задайте тот же пароль в переменной среды `HOTEL_DB_PASSWORD`.

`CREATE USER IF NOT EXISTS` не изменяет пароль уже существующего пользователя. Если пользователь уже создан, проверьте его настройки отдельно. При работе с нестандартным сервером также проверьте соответствие MySQL-аккаунта `'hotel_course_admin'@'localhost'` выбранному адресу подключения.

### 2. Установить зависимости и запустить

Windows / PowerShell — активация виртуального окружения не обязательна:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:HOTEL_DB_PASSWORD = "ваш_локальный_пароль"
.\.venv\Scripts\python.exe main.py
```

Linux / Bash (в том числе Arch Linux):

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
export HOTEL_DB_PASSWORD='ваш_локальный_пароль'
.venv/bin/python main.py
```

Настройки подключения читаются из переменных среды:

| Переменная | Значение по умолчанию |
| --- | --- |
| `HOTEL_DB_HOST` | `127.0.0.1` |
| `HOTEL_DB_PORT` | `3306` |
| `HOTEL_DB_USER` | `hotel_course_admin` |
| `HOTEL_DB_PASSWORD` | пустая строка — задайте явно |
| `HOTEL_DB_NAME` | `hotel_db` |

`.env.example` служит только справочником. Приложение **не читает `.env` автоматически**: копирование файла само по себе не настроит подключение. Не публикуйте свои пароли или выгрузки настоящих данных.

### 3. Демо-аккаунты

| Роль | Логин | Демо-пароль |
| --- | --- | --- |
| Администратор | `admin` | `admin123` |
| Менеджер | `manager` | `manager123` |
| Гость | `guest` | `guest123` |

Эти пароли опубликованы специально для локальной демонстрации и не должны использоваться в рабочей системе. Новый аккаунт, созданный через интерфейс, всегда получает роль `guest`.

## Структура

```text
HotelMOST/
├── main.py                 # запуск QApplication
├── database.sql            # схема и demo-записи
├── requirements.txt
├── .env.example            # справочник настроек
├── hotel_app/
│   ├── auth.py             # вход и регистрация
│   ├── admin.py            # номера и аналитика
│   ├── manager.py          # заезды и выезды
│   ├── guest.py            # поиск и заявки
│   ├── db.py               # соединения и SQL-запросы
│   ├── config.py           # параметры из среды
│   ├── reporting.py        # диаграммы и PDF
│   ├── styles.py           # тема интерфейса
│   └── widgets.py          # общие элементы UI
└── tests/                  # небольшие проверки конфигурации и demo-хешей
```

База состоит из четырёх таблиц: `users`, `rooms`, `guests`, `bookings`. Бронирование связано внешними ключами с пользователем, гостем и номером. Оформление заезда и выезда выполняется в транзакциях.

## Проверки

После установки зависимостей:

```bash
python -m unittest discover -s tests -v
python -m compileall -q main.py hotel_app tests
```

Команды выполняйте Python-интерпретатором виртуального окружения (`.venv/bin/python` на Linux или `.\.venv\Scripts\python.exe` в PowerShell). Тесты проверяют чтение конфигурации из среды, отсутствие встроенного пароля БД и соответствие demo-паролей хешам в SQL. Они не подключаются к MySQL и не покрывают весь интерфейс или бизнес-логику.

Для ручной демонстрации на чистой учебной базе: войдите каждой ролью; создайте заявку гостя; отдельно оформите заезд менеджером; проверьте данные администратора; оформите выезд; сохраните PDF и проверьте обе страницы.

## Ограничения и возможное развитие

- Пароли приложения сейчас хранятся как SHA-256 без соли. Для реального использования нужна специализированная схема хранения паролей и новая модель авторизации.
- Роли разделяют интерфейсы, но приложение подключается к MySQL одним общим пользователем. Это не серверная граница безопасности; доступ к базе нельзя выдавать недоверенным клиентам.
- Заявка гостя не преобразуется в заезд автоматически: отдельного сценария подтверждения или отмены заявки пока нет.
- После выезда номер получает статус `cleaning`; отдельного действия для возврата в `free` в интерфейсе пока нет.
- Проверка доступности при поиске не защищает от одновременных бронирований. Сценарий менеджера также требует единой проверки пересечения дат.
- SQL выполняется в потоке интерфейса; при медленном соединении окно может зависать. Обработка ошибок и валидация полей пока базовые.
- Полный end-to-end сценарий, развёртывание на Linux и нагрузочная работа требуют дополнительных проверок. Проект предназначен для локального обучения; не вводите в него настоящие паспортные или контактные данные.

Следующие шаги: выделить бизнес-логику из окон, добавить тесты бронирований, завершить жизненный цикл заявок и номеров, улучшить авторизацию. Backend/API можно реализовать отдельным этапом.
